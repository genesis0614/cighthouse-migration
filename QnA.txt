[01] 프로젝트와 본인 역할 (1-8)

Q01. Cighthouse 프로젝트의 목표와 서울·싱가포르 리전을 사용한 이유를 설명해 주세요.
A01. Cighthouse는 서울의 기존 EC2 기반 웹 서비스와 MySQL을 싱가포르의 EKS 기반 서비스로 옮기고, Route
     53을 이용해 단계적 트래픽 전환을 시도하는 프로젝트입니다. 저는 그중 DMS를 전담했습니다.

Q02. 본인이 전담한 DMS 업무의 시작부터 검증까지 책임 범위를 설명해 주세요.
A02. 저는 [직접 담당한 endpoint/task/네트워크/검증 범위]를 맡았습니다. 실제로 수행한 설정, 확인한 결과, 다른 팀원
     담당 영역을 구분해서 답변하겠습니다.

Q03. 기존 서울 MySQL 데이터베이스에서 싱가포르 데이터베이스로 데이터가 이동하는 경로를 설명해 주세요.
A03. DMS replication instance가 source endpoint로 서울 MySQL에 접속해 변경 데이터를 읽고,
     VPC 연결을 통해 target endpoint인 싱가포르 MySQL에 전달합니다. 이를 위해 두 VPC의 라우팅과 DB 보안
     그룹도 연결 경로를 허용해야 합니다.

Q04. DMS replication instance, source endpoint, target endpoint,
     replication task는 각각 어떤 역할을 하나요?
A04. Replication instance는 복제 작업을 수행하는 컴퓨팅 자원이고, endpoint는 소스/대상 DB 연결 정보를
     정의합니다. Replication task는 두 endpoint 사이에서 어떤 테이블을 어떤 방식으로 복제할지 지정합니다.

Q05. 이 프로젝트에서 DMS를 선택한 이유는 무엇이며, dump/restore나 자체 복제 방식과 비교하면 어떤 장점이 있나요?
A05. DMS는 초기 적재와 지속적인 변경 데이터 복제를 지원해 애플리케이션 중단 시간을 줄이는 데 적합합니다.
     Dump/restore는 간단하지만 서비스 변경을 반영하려면 별도 동기화·전환 절차가 필요하고, 자체 복제는 개발·운영 부담이
     큽니다.

Q06. README의 아키텍처 설명과 실제 배포·검증 상태를 어떻게 구분해 설명하겠습니까?
A06. README에는 목표 아키텍처와 배포 명령이 설명되어 있지만, 문서에 있다는 사실만으로 실제 배포·검증 완료라고 말할 수는
     없습니다. 제가 직접 실행한 리소스와 로그·테스트 결과만 완료 사실로 말하고 나머지는 계획/문서로 구분하겠습니다.

Q07. DMS 작업 중 가장 어려웠던 문제와 원인 분석·해결 과정을 설명해 주세요.
A07. [오류와 영향]이 있었고, [DMS task 로그/endpoint test/CloudWatch 지표]를 확인해 [원인]으로
     좁혔습니다. [조치] 후 [데이터 검증 또는 재시작 결과]를 확인했습니다. 실제 겪은 사례로 채우겠습니다.

Q08. 데이터 마이그레이션 성공을 기술적·업무적 관점에서 어떻게 정의했나요?
A08. 기술적으로는 전체 대상 테이블 적재, CDC 지연이 허용 범위 이내, 데이터 정합성 확인, task 안정 상태가 기준입니다.
     업무적으로는 전환 중 허용 가능한 중단 시간과 오류율을 지키고, 롤백 가능한 상태를 유지하는 것입니다.

────────────────────────────────────────────────────────────────────────
[02] AWS DMS 기초·구성요소 (9-18)
────────────────────────────────────────────────────────────────────────
Q09. DMS의 full load, CDC, full load + CDC 방식은 각각 무엇이며 어떤 상황에 선택하나요?
A09. Full load는 기존 데이터를 한 번 적재하고, CDC는 이후 발생한 변경분을 계속 복제합니다. Full load +
     CDC는 초기 적재와 변경분 동기화를 함께 수행해 다운타임을 줄여야 할 때 적합합니다.

Q10. CDC는 MySQL의 변경사항을 어떤 방식으로 읽어 대상 DB에 반영하나요?
A10. DMS는 MySQL 소스의 binary log를 읽어 변경 이벤트를 수집하고 대상 DB에 적용합니다. 안정적인 CDC를 위해
     binlog 보존 기간, 포맷, 사용자 권한과 소스 부하를 사전에 확인해야 합니다.

Q11. MySQL 소스에서 CDC를 사용하기 위해 사전에 확인해야 할 binlog 설정과 권한은 무엇인가요?
A11. RDS MySQL의 binlog 활성화/보존 설정과 `ROW` 포맷 등 DMS가 지원하는 조건을 확인합니다. 전용 복제
     사용자에 필요한 권한만 주고, 바이너리 로그가 복제 지연보다 오래 보존되는지 확인해야 합니다.

Q12. DMS replication instance의 인스턴스 클래스와 스토리지는 처리량·복제 지연에 어떤 영향을 주나요?
A12. 인스턴스의 CPU·메모리·네트워크는 읽기, 변환, 전송, 적용 속도에 영향을 줍니다. 스토리지는 로그와 캐시 및 full
     load 작업에 필요하므로 지표와 데이터량을 보고 선택하고, 과대/과소 할당을 피해야 합니다.

Q13. Source endpoint와 target endpoint에서 연결 정보 외에 각각 확인해야 할 설정은 무엇인가요?
A13. Source는 binlog 접근·소스 DB 버전·보존 설정과 연결 권한을 확인하고, Target은 스키마 준비·쓰기
     권한·용량·인덱스·SSL을 확인합니다. 양쪽 모두 주소·포트·DB 이름·자격 증명과 연결 테스트가 필요합니다.

Q14. DMS replication subnet group은 어떤 목적으로 사용되며, 여러 AZ에 배치해야 하는 이유는 무엇인가요?
A14. Replication subnet group은 DMS replication instance가 생성될 VPC subnet 집합을
     지정합니다. 서로 다른 AZ의 subnet을 포함하면 배치 선택과 Multi-AZ 구성의 기반이 되고, 각 subnet에서
     DB까지 라우팅이 가능해야 합니다.

Q15. DMS task의 table mapping과 selection rule은 어떤 방식으로 대상 스키마와 테이블을 선택하나요?
A15. Table mapping의 selection rule은 schema/table 패턴으로 포함·제외할 객체를 고릅니다.
     프로젝트의 `%` 규칙은 모든 스키마와 테이블을 포함하므로, 운영에서는 대상 범위를 명시하고 제외 규칙을 검토해야 합니다.

Q16. MySQL에서 MySQL로 마이그레이션할 때 DMS가 처리하는 데이터 이동과 스키마 준비의 범위는 어떻게 구분되나요?
A16. DMS는 주로 테이블 데이터 이동과 CDC를 수행하지만 모든 스키마 객체·사용자·권한·프로시저를 자동으로 완전 이전한다고
     가정하면 안 됩니다. 필요한 스키마와 인덱스, 제약, 트리거 등을 별도 생성·검증할 계획이 필요합니다.

Q17. DMS task의 상태와 replication task statistics만으로 성공을 판단하기 어려운 이유는 무엇인가요?
A17. Task 상태는 처리 파이프라인 상태이지 데이터가 정확하고 완전하다는 증거는 아닙니다. 테이블별 적재 통계, 오류, CDC
     지연을 보고 row 수·샘플·업무 쿼리 등으로 대상 데이터를 검증해야 합니다.

Q18. DMS의 CDCLatencySource와 CDCLatencyTarget 같은 지표는 각각 무엇을 보여주나요?
A18. CDCLatencySource는 소스에서 변경 이벤트를 읽어오는 지연, CDCLatencyTarget은 변경 이벤트가 대상에
     적용되기까지의 지연을 보여줍니다. 둘을 함께 보고 소스 캡처와 대상 적용 중 어느 쪽이 병목인지 판단합니다.

[03] DMS 설계·구현 (19-33)
────────────────────────────────────────────────────────────────────────
Q19. 이 프로젝트에서 복제 인스턴스를 서울 리전에 둔 선택의 장점과 제약은 무엇인가요?
A19. 서울의 소스 DB와 가까워 source 연결 지연을 줄이고 소스 측 운영을 단순화할 수 있습니다. 반면 싱가포르 대상까지 리전
     간 네트워크와 VPC Peering을 안정적으로 구성해야 하고, 전송 비용·지연·리전 장애 영향을 고려해야 합니다.

Q20. 서울 소스와 싱가포르 대상 DB 사이에서 DMS가 연결되려면 VPC, 서브넷, 라우팅은 어떻게 구성되어야 하나요?
A20. DMS 인스턴스 subnet에서 source DB와 target DB 주소까지 각각 경로가 있어야 합니다. 서울과 싱가포르
     CIDR이 겹치지 않아야 하며 Peering 연결, 양쪽 route table, 보안 그룹/NACL, DNS 해석을 모두 맞춰야
     합니다.

Q21. VPC Peering을 통해 DMS에서 양쪽 DB로 연결할 때 양방향 라우트와 보안 그룹 규칙을 어떻게 설계하나요?
A21. Peering은 양쪽 VPC route table에 상대 CIDR 경로가 필요하며 전이 라우팅은 제공하지 않습니다. DMS의
     사설 주소 범위에서 DB 포트만 허용하도록 각 DB 보안 그룹과 NACL을 최소 범위로 구성하겠습니다.

Q22. DMS가 DB에 연결되지 않을 때 엔드포인트 테스트, DNS, 라우팅, NACL, 보안 그룹을 어떤 순서로 점검하겠습니까?
A22. 우선 DMS에서 endpoint connection test를 수행해 상세 오류를 확인합니다. 이어 endpoint
     주소/DNS와 포트, DMS subnet에서의 경로, Peering 상태와 양쪽 route table, 보안 그룹
     ingress/egress, NACL 반환 경로를 차례로 점검합니다.

Q23. DMS replication instance를 배치할 subnet group과 연결 보안 그룹을 어떻게 정하고 최소 권한으로
     제한하겠습니까?
A23. DMS subnet group에는 DB까지 라우팅되는 private subnet을 사용하고, 가용성이 필요하면 여러 AZ를
     포함합니다. DMS 전용 보안 그룹을 만들고 DB 포트만 필요한 source/target CIDR에 허용하며, 관리 접근은
     제한합니다.

Q24. 소스 DB와 대상 DB endpoint에 저장되는 자격 증명을 안전하게 관리하려면 어떤 방법을 사용하겠습니까?
A24. Endpoint credentials를 Secrets Manager에 저장하고 DMS가 필요한 secret만 읽도록 IAM
     role을 제한하겠습니다. 비밀번호 교체 절차를 마련하고 로그·명령 기록·Terraform state에도 비밀이 노출되지 않는지
     확인합니다.

Q25. CLI 명령행에 비밀번호를 직접 전달하는 방식은 어떤 위험이 있으며 안전한 대안은 무엇인가요?
A25. 명령행 인자는 shell history, 프로세스 목록, CI 로그에 남을 수 있습니다. Secrets Manager, AWS
     CLI의 보안된 입력 경로 또는 보호된 자동화 자격증명을 사용하고 출력·로그에 비밀이 기록되지 않게 하겠습니다.

Q26. README에 기재된 `admin` 계정을 DMS용으로 그대로 사용하는 것의 문제와 필요한 DB 권한을 설명해 주세요.
A26. 공용 `admin` 계정은 권한이 과도하고 노출 시 피해가 커지며 감사와 회전도 어렵습니다. CDC에 필요한 binlog 읽기
     및 복제 작업 권한만 가진 전용 계정과 대상 쓰기 계정을 분리해 사용하겠습니다.

Q27. 대상 엔드포인트 생성 명령의 AWS 리전, 대상 RDS 리전, replication instance 리전은 어떻게 구분하고
     검증해야 하나요?
A27. DMS replication instance와 endpoint 리소스는 DMS API 리전에 생성되고, target DB는
     hostname/port를 통해 다른 리전에서 접근할 수 있습니다. README처럼 DMS 리전에 endpoint를 만들되
     주소가 실제 싱가포르 RDS인지, Peering과 DNS 경로가 되는지 검증합니다.

Q28. README의 task 생성 예시는 migration type을 CDC로 지정합니다. 대상 DB가 비어 있다면 초기 데이터
     적재를 어떻게 보장하겠습니까?
A28. CDC 전용 task는 이후 변경만 복제하므로 빈 target에 기존 레코드가 자동으로 생기지 않습니다.
     `full-load-and-cdc` task를 사용하거나 검증된 초기 full load를 먼저 수행하고, CDC 시작 위치와
     누락 없는 연속성을 확인해야 합니다.

Q29. Full load + CDC를 선택할 때 초기 적재 중 발생하는 변경사항이 누락되지 않도록 어떤 순서로 처리되나요?
A29. Full load + CDC는 초기 테이블 적재와 함께 변경 이벤트를 포착해 적재 중 발생한 변경도 적용하도록 설계됩니다.
     실제 task 시작 위치·테이블별 상태·지연을 확인하고, 소스 변경분이 모두 대상에 반영된 시점을 검증해야 합니다.

Q30. Migration task를 시작하기 전에 source와 target의 schema, table, index, 데이터 타입
     호환성을 어떻게 점검하겠습니까?
A30. 두 DB의 엔진/버전과 schema/table 이름, 문자셋·collation, 데이터 타입, nullability, PK,
     인덱스, 제약을 비교합니다. DMS가 자동 처리하지 않는 스키마 객체와 권한은 사전 생성하고 테스트 데이터로 변환 결과를
     확인합니다.

Q31. 대용량 테이블이나 LOB 컬럼이 있을 때 task 설정과 적재 성능에 어떤 영향을 고려하겠습니까?
A31. LOB 크기와 모드, 컬럼 제한, 메모리·네트워크 사용량이 적재 속도와 잘림/누락에 영향을 줄 수 있습니다. 대표 LOB
     데이터를 시험하고 task 설정과 처리량, 대상 DB 부하를 측정해 적절한 모드를 선택합니다.

Q32. DMS throughput이 낮거나 replication instance의 CPU·메모리 사용량이 높다면 어떤 요인을
     조정하겠습니까?
A32. 우선 CloudWatch에서 CPU·메모리·디스크·네트워크, CDC 지연과 테이블 오류를 봅니다. 병목이 replication
     instance인지, source binlog 읽기인지, 네트워크인지, target 쓰기/인덱스인지 구분한 뒤 인스턴스 크기,
     병렬도, 테이블 단위 적재를 조정합니다.

Q33. DMS 로그, CloudWatch 지표, endpoint test 결과를 이용해 배포 검증 기록을 어떻게 남기겠습니까?
A33. Task/endpoint 식별자와 설정 변경 이력을 기록하고, endpoint test 결과, task 로그, 테이블 통계,
     CloudWatch 지표와 검증 결과를 시간대별로 남깁니다. 비밀번호나 민감한 연결 정보는 기록에서 제거합니다.

────────────────────────────────────────────────────────────────────────
[04] 검증·장애·전환 (34-42)
────────────────────────────────────────────────────────────────────────
Q34. 전체 row count, 샘플 데이터, checksum 또는 업무 쿼리를 이용해 마이그레이션 데이터 정합성을 어떻게
     확인하겠습니까?
A34. 모든 대상 테이블의 row count를 비교하고 PK 기준 샘플과 중요 업무 쿼리를 대조합니다. 가능하면 checksum이나
     DMS validation을 사용하되, 쓰기 중인 데이터는 같은 시점 기준으로 비교하고 큰 테이블은 범위별로 나눕니다.

Q35. DMS의 데이터 검증 기능을 켜는 경우 어떤 장점과 추가 부하·운영상 고려사항이 있나요?
A35. DMS validation은 소스와 대상의 데이터 일치를 확인하는 데 도움이 됩니다. 데이터량이 크면 추가 읽기 부하와 복제
     자원 사용, 검증 지연이 생길 수 있어 대상 범위와 수행 시점을 조절해야 합니다.

Q36. Replication task가 실패하거나 테이블이 오류 상태라면 원인과 재시작 가능 여부를 어떻게 판단하겠습니까?
A36. Task 로그와 table statistics에서 실패 테이블, 권한·스키마 오류, 연결 단절, 리소스 부족을 분류합니다.
     체크포인트와 중복 적용 가능성을 확인해 resume가 안전한지 판단하고, 필요하면 테이블 재적재나 새 task를 계획합니다.

Q37. CDC 지연이 계속 증가한다면 소스 변경량, 네트워크, 인스턴스 용량, 대상 DB 성능 중 무엇을 조사하겠습니까?
A37. Source latency가 높으면 binlog 수집·소스 부하·네트워크를, target latency가 높으면 대상 DB
     쓰기 용량·인덱스·잠금과 복제 인스턴스 자원을 봅니다. 변경량 증가와 네트워크 지표도 함께 비교해 병목을 좁힙니다.

Q38. 소스 DB의 binlog가 정리되어 CDC가 중단되는 일을 예방하려면 어떤 설정과 모니터링이 필요하나요?
A38. 소스 binlog 보존 시간을 예상 최장 지연보다 충분히 길게 설정하고 CDC latency와 binlog 여유를
     모니터링합니다. 복제 중단 시 필요한 로그가 사라지지 않도록 알림을 두고, task 복구·재동기화 절차를 테스트합니다.

Q39. 무중단 전환 전에 애플리케이션 쓰기 중단, 최종 CDC 적용, 데이터 검증, 연결 변경을 어떤 순서로 수행하겠습니까?
A39. 전환 창을 공지하고 소스 쓰기를 멈추거나 읽기 전용으로 바꿉니다. CDC 지연이 허용 기준에 도달할 때까지 기다린 뒤 데이터
     검증, 대상 서비스 연결 변경, 읽기/쓰기 smoke test 순으로 진행하고 모니터링합니다.

Q40. 전환 중 예상치 못한 데이터 불일치나 지연이 발견되면 롤백 기준과 절차를 어떻게 정하겠습니까?
A40. 데이터 불일치, 지연, 오류율 등 수치화한 기준을 넘으면 전환을 중단하거나 되돌립니다. 서울의 원본을 보존하고 싱가포르 쓰기를
     통제해 역방향 복제 여부를 검토하며, 재전환 전에 양쪽 데이터의 일관성을 확인해야 합니다.

Q41. 서울과 싱가포르 서비스가 동시에 쓰기를 수행하면 어떤 데이터 충돌 위험이 있으며 어떻게 방지하겠습니까?
A41. 양쪽 서비스가 같은 논리 데이터를 동시에 쓰면 순서 역전, 충돌, 중복 또는 split-brain이 생길 수 있습니다. 전환
     시점에는 단일 writer 원칙을 지키고, 양방향 쓰기가 꼭 필요하다면 충돌 해결과 키/일관성 설계를 별도로 해야 합니다.

Q42. Route 53 weighted routing을 50:50으로 설정하는 것만으로 안전한 Blue-Green 전환이나 자동
     Failover가 보장되나요? 무엇을 추가해야 하나요?
A42. 아닙니다. Weighted DNS는 DNS 응답을 비율로 분배할 뿐 resolver caching, 세션, 애플리케이션 상태와
     DB 일관성까지 해결하지 않으며 50:50이 정확한 요청 비율을 보장하지 않습니다. Health check/failover
     정책, 단계적 가중치 변경, 데이터 동기화·롤백 절차와 실제 트래픽 검증이 필요합니다.

────────────────────────────────────────────────────────────────────────
[05] 보안·가용성·비용·개선 (43-50)
────────────────────────────────────────────────────────────────────────
Q43. README에 기재된 RDS 보안 그룹의 `0.0.0.0/0` MySQL ingress 규칙은 어떤 위험이 있으며 어떻게
     좁히겠습니까?
A43. `0.0.0.0/0`의 3306 ingress는 광범위한 접근 허용으로 공격 표면과 오설정 위험을 키웁니다. RDS를
     private로 유지하고 DMS의 필요한 주소 범위나 통제된 source security group에서만 DB 포트를
     허용하겠습니다.

Q44. RDS 저장 데이터와 DMS 전송 데이터를 암호화하려면 각각 어떤 설정을 확인해야 하나요?
A44. RDS 저장 암호화는 KMS 기반 storage encryption과 백업/스냅샷 정책을 확인합니다. 전송은 DMS
     endpoint와 MySQL 간 TLS/SSL을 구성·검증하고, DMS replication storage와 로그의 암호화 및
     KMS 권한도 점검합니다.

Q45. RDS master password를 CloudFormation 템플릿에 평문으로 두지 않으려면 어떻게 개선하겠습니까?
A45. 비밀번호를 템플릿에서 제거하고 Secrets Manager에 저장한 뒤 CloudFormation dynamic
     reference 또는 DMS endpoint의 Secrets Manager 연동을 사용하겠습니다. Secret 접근 role을
     최소화하고 회전·배포 절차를 마련합니다.

Q46. RDS backup retention이 0일 때 복구와 전환 안전성에 어떤 영향이 있으며, 적절한 백업 정책은 어떻게
     정하겠습니까?
A46. Retention 0은 자동 백업을 제공하지 않아 시점 복구와 장애 후 원상 복구가 어려워집니다. RPO/RTO와 보존 요구에
     맞춰 자동 백업 기간을 정하고, 스냅샷·복구 테스트 및 전환 기간의 별도 보호책을 마련해야 합니다.

Q47. 단일 DMS replication instance의 장애나 AZ 장애에 대비해 복구·재개 전략을 어떻게 설계하겠습니까?
A47. 복제 인스턴스의 복구 가능한 설정과 task checkpoint를 보존하고, Multi-AZ 지원 여부와 재생성 시간을
     확인하겠습니다. 장애 감지 알림, task 재개 또는 재생성, binlog 보존, endpoint 재연결, 데이터 재검증을
     포함한 runbook을 테스트합니다.

Q48. DMS replication instance의 크기와 실행 시간을 최적화해 비용을 관리하면서 목표 RPO/RTO를 만족시키려면
     어떻게 하겠습니까?
A48. 예상 데이터량·변경률·목표 지연을 기준으로 작은 인스턴스에서 부하 테스트 후 필요한 크기로 조정합니다. 복제 완료 후 불필요한
     인스턴스를 종료하되, 요구 RPO/RTO와 롤백 기간 중 필요한 리소스 비용은 유지합니다.

Q49. 프로젝트에서 본인이 직접 수행한 DMS 테스트 결과와, 문서상 제안에 그친 사항을 구분해 설명해 주세요.
A49. 실제 증거로 답변해야 합니다. [직접 생성한 리소스와 task 유형], [endpoint test/task 로그], [검증한
     테이블·row count·CDC 지연], [발생한 오류와 해결 결과]를 제시하고 실행하지 않은 항목은 설계 또는 README
     내용이라고 분명히 하겠습니다.

Q50. 다시 설계한다면 마이그레이션 전·중·후에 어떤 자동화와 검증 절차를 추가하고, 성공 기준은 무엇으로 측정하겠습니까?
A50. 사전에는 endpoint 연결·권한·스키마 검증, 진행 중에는 latency·오류·테이블 적재 자동 점검, 종료에는 정합성
     검사와 전환 승인 단계를 자동화하겠습니다. 성공 기준은 데이터 누락 0, 허용 지연 이내, 목표 전환 시간과 검증된 롤백 절차로
     측정합니다.
